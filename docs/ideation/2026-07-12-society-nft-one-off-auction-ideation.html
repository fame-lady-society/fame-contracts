Society NFT One-Off Auction

A deliberately small Base auction for one Society NFT: native ETH, one live top bid, immediate refunds, no administrative escape hatch after custody, and settlement that cannot be held hostage by recipient callbacks.

Evidence before cleverness

Grounding Context

Codebase Context. The Society NFT mirror address 0xbb5ed04dd7b207592429eb8d599d103ccad646c4 is already a canonical Base public constant. The local DN404Mirror exposes the normal ERC-721 ownership, approval, transferFrom, and safeTransferFrom surface. The auction should use only that mirror surface; no ERC-20 call, allowance, rescue, or WETH path belongs here.

FameLaunch supplies the repo’s minimal receiver pattern. FameRouter is the stronger safety precedent: validate value before movement, apply a reentrancy guard around external calls, update effects before interactions, and keep business accounting independent from ambient balances. The existing repository has no auction contract or hostile-refund fixture yet.

External prior art confirms the core tradeoff: pushed ETH refunds can block progress when the recipient rejects payment, while ERC-721 safe delivery gives winner-controlled code a callback that can reject settlement. The user made the refund policy explicit: a bidder who rejects their outbid refund donates that amount to the seller. This means the honest accounting statement is “current top bid plus tracked failed-refund donations,” not literally “only the top bid” after a failed refund.

Scope lock. “Top-bid” here means a single lot, no reserve, strictly higher bids, no Dutch price curve, no minimum increment beyond “higher,” no anti-sniping extension, no royalty/fee engine, no proxy, and no reusable marketplace framework.

Idea 1 · Top pickOne-Transaction Ignition

Confidence 92%Complexity Medium
Description
Make start(tokenId) the only activation path. In one atomic transaction it targets the fixed Society mirror, validates token existence and current owner, confirms transfer authority, records startTime from the activation block and derives endTime = startTime + 3 days, pulls the NFT, verifies post-transfer custody, and then crosses a one-way activation boundary. Any failed flight check rolls the whole operation back.
Axis
Start and NFT custody flight checks
Basis
direct: DN404Mirror exposes authoritative ownerOf, approval, and ERC-721 transfer behavior; the repo already uses one-way launch state and explicit preflight checks.
Rationale
The seller cannot open bidding while retaining the ability to move the prize or revoke an approval. Successful activation itself proves the advertised NFT is escrowed.
Downsides
The start transaction performs an external NFT transfer and must be carefully guarded. The receiver can validate safe receipts, but cannot stop somebody from later forcing an unrelated NFT into the contract through plain transferFrom; the contract should avoid claiming otherwise.

Illustrative only: complexity stays before the trust commitment; the live auction stays boring.

Idea 2Non-Vetoable Bid Replacement

Confidence 90%Complexity Medium
Description
A bid must be positive, arrive during the active half-open window, and strictly exceed the stored top bid. The contract records the new leader before attempting a guarded native-ETH refund to the prior leader. If the refund recipient rejects the call, the new bid still succeeds; the rejected amount is recorded as seller proceeds and an explicit donation event is emitted.
Axis
Bidding, immediate refunds, and rejected-refund donations
Basis
direct: Existing native helpers revert when a recipient rejects ETH, while FameRouter supplies the local reentrancy and effects-before-interactions precedent. reasoned: A previous leader’s callback behavior must not give them a veto over later bids.
Rationale
This preserves the product’s immediate-refund feel for normal EOAs while turning hostile or incompatible recipients into a deterministic economic outcome chosen by the user: donation, not deadlock.
Downsides
This policy is intentionally harsh and nonstandard. The refund gas policy must be generous and documented so a merely expensive receiver is not accidentally classified as refusing payment; bidders using contracts must understand that rejection forfeits the refund.

Both branches preserve the new high bid; recipient behavior changes only where the old funds are accounted.

Idea 3Half-Open Custody Fuse

Confidence 95%Complexity Low
Description
Use one unambiguous boundary: bids are valid for startTime <= block.timestamp < endTime; settlement is valid for block.timestamp >= endTime. Once ignition succeeds, the owner has no pause, cancellation, extension, early-settlement, deadline-edit, or NFT-rescue function until the terminal settlement path executes.
Axis
Time window and irreversible lifecycle
Basis
direct: Existing repo windows demonstrate the ambiguity created when bidding-like actions and post-deadline actions both include the exact end timestamp. The repo also contrasts reversible administrative controls with a one-way launch flag.
Rationale
At the exact end second only settlement is legal, and bidder trust comes from absent privileged controls rather than an owner promise not to use them.
Downsides
Operational mistakes made before start cannot be repaired after ignition. That is the point, but it raises the quality bar for preflight checks and dry-run deployment.

Idea 4Settlement the Winner Cannot Block

Confidence 88%Complexity Low
Description
After the deadline, anyone can settle. The contract records terminal state before external interaction, then uses the mirror’s plain ERC-721 transferFrom to register title to the winner without invoking winner-controlled receiver code. If there were no bids, the same terminal path returns the NFT to the owner. Seller payment is not attempted during settlement.
Axis
Permissionless settlement and NFT delivery
Basis
direct: DN404Mirror.safeTransferFrom forwards into onERC721Received and bubbles rejection; plain transferFrom does not call the recipient. Existing callback tests show how a rejecting recipient can roll back a coupled flow.
Rationale
Permissionless settlement is meaningful only if the winner cannot make every resolver fail. Treat the NFT transfer like a title-registry update, not a parcel requiring the recipient’s signature.
Downsides
A winning contract that cannot later operate the NFT may strand its own asset. This deliberately places address suitability on the bidder to preserve auction liveness. The no-bid return path and repeated-settlement guard need explicit tests.

Idea 5Tracked Proceeds With a Retryable Owner Exit

Confidence 91%Complexity Low
Description
Track the live top bid, failed-refund donations, and settled owner proceeds as explicit state transitions rather than using address(this).balance as the business ledger. Failed-refund donations remain locked during the active auction; no owner withdrawal is available before terminal settlement. Settlement converts the final bid and accumulated donations into owner proceeds. The owner then withdraws the exact proceeds to a chosen payable recipient; accounting clears before the call, and a rejected destination reverts so the owner can retry with another address.
Axis
Proceeds accounting and owner withdrawal
Basis
direct: FameRouter separates route-local accounting from ambient balances. Existing native withdrawal paths show why a fixed rejecting recipient can block coupled work. reasoned: Forced ETH can make raw balance larger than the contract’s obligations, so state—not balance—must define proceeds.
Rationale
Tests, indexers, and humans can reconcile every economically meaningful wei, while accidental or forcibly sent ETH cannot corrupt bid comparisons or enable double withdrawal.
Downsides
A policy is still needed for unavoidable excess ETH that is not part of the tracked ledger: leave it inert, or allow an owner-only post-settlement excess sweep. Keeping that policy post-settlement avoids creating a live-auction escape hatch.
